# Skill: architecture-check

> **触发条件**：任何涉及架构变更的需求（新增维度/跨模块/数据模型变更）开始前，必须先过这个 checklist。

---

## 快速扫描 Checklist（必须全部过一遍）

### 重复逻辑
- [ ] 这个功能的核心逻辑，是否已经在其他地方实现过类似的？
- [ ] 实现后，相同逻辑是否会出现在 2+ 个文件？

**→ 是：先抽取，再实现新功能**

### 新"维度"引入
- [ ] 这个功能是否引入了新的"维度"？
  - 主题（新增一种主题类型）
  - 布局（新增一种布局模式）
  - 格式（新增一种导出格式）
  - 颜色规则（新增一条颜色逻辑）
- [ ] 这个维度是否有统一的入口管理？

**→ 有新维度但无统一入口：先建配置层，再实现功能**

### 文件体积
- [ ] 涉及的文件当前行数？
- [ ] 修改后预计行数是否超过 500 行？

**→ 会超过：先规划拆分方案（抽 hook、抽 util）**

### 数据来源
- [ ] 这个功能依赖的数据，来源是否唯一（Single Source of Truth）？
- [ ] 是否有从多处推断/反推同一个值的情况？

**→ 多处推断：指定单一来源，其他地方读这里**

### 现有规则兼容
- [ ] 是否与 AGENTS.md 第 10 节的全局颜色规则冲突？
- [ ] fill / border 是否保持互斥？
- [ ] 用户手动颜色是否优先于主题注入？
- [ ] 主题 ID 是否仍然存在 root.data.appliedTheme（不反推）？

---

## 发现问题时

**禁止沉默推进**。必须：
1. 向用户说明：发现了什么架构问题
2. 说明不处理的代价（"如果不处理，会在 X 处引入技术债"）
3. 说明处理的收益（"处理后，改 1 处 vs 改 N 处"）
4. 获得用户明确确认后，才能开始重构或推进

---

## 架构决策记录

每次做出架构决策（包括"不改"也是一种决策），必须记录到：
`project-management/decision-log.md`

格式：
```
日期: YYYY-MM-DD
决策: [一句话]
原因: [为什么这样决策]
代价: [这个决策的约束/风险]
```

---

## 架构检查后需要补写规则时：信息写入路由

架构检查完毕，如果需要新增规则或文档，先判断类型：

| 内容类型 | 写入位置 |
|---------|---------|
| 产品交互行为规则（如颜色互斥、状态机） | `docs/product/` 对应文件 |
| 架构决策（为什么这样设计） | `project-management/decision-log.md` |
| 开发踩坑记录 | `LEARNINGS.md` |
| AI 协作流程规则 | `AGENTS.md` 或 `skills/` 对应 SKILL.md |

**禁止把产品规则或架构约束直接写进 AGENTS.md 正文。**
AGENTS.md 第 10 章只保留指向 `docs/product/` 的引用指针。
