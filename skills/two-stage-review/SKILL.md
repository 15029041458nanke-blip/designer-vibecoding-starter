# Skill: two-stage-review

> **触发条件**：每个 task 完成后，必须顺序执行两阶段 review。两阶段都通过，才算这个 task 完成。

---

## 两阶段必须顺序执行，不得跳过或合并

```
Task 实现完成
    ↓
阶段 1：Spec 合规 Review（先做这个）
    ↓ 通过
阶段 2：代码质量 Review（再做这个）
    ↓ 通过
Task 完成 ✅
```

**阶段 1 未通过，禁止进行阶段 2。**

---

## 阶段 1：Spec 合规 Review

对照 plan/spec，逐条检查：

### Checklist
- [ ] spec 中每条需求，代码里是否有对应实现？（逐条核对）
- [ ] 有没有实现了 spec 以外的功能？（over-engineering 也算问题）
- [ ] 所有边界条件是否处理了？（空值、异常输入、极端情况）
- [ ] 所有错误处理是否到位？

### 结论
- **通过**：每条 spec 需求都有对应实现，且没有超出 spec 范围
- **未通过**：列出具体缺失项 → 实现者修复 → 重新做阶段 1

---

## 阶段 2：代码质量 Review

### Checklist
- [ ] TypeScript 类型安全（无 `any`，接口签名正确）
- [ ] 是否遵循项目规则（参见 AGENTS.md 第 10 节全局颜色规则等）
- [ ] 相同逻辑是否超过 2 处（→ 应抽取为函数/常量）
- [ ] 文件行数是否接近 500 行（→ 提醒拆分）
- [ ] 是否有明显的回归风险（改了 A，B 会不会受影响？）
- [ ] 关键逻辑是否有注释说明意图（不是解释代码，是解释为什么）

### 严重程度分级

| 级别 | 含义 | 处理方式 |
|---|---|---|
| 🔴 Critical | 功能错误 / 数据丢失风险 / 类型系统漏洞 | 必须修复后重新 review |
| 🟡 Important | 代码重复 / 规则违反 / 回归风险 | 建议修复，酌情处理 |
| 🟢 Minor | 命名不够清晰 / 注释可以更好 | 记录即可，不阻塞 |

### 结论
- **通过**：无 Critical 问题，Important 问题已处理或有说明
- **未通过**：列出 Critical 问题 → 修复 → 重新做阶段 2

---

## 此 Skill 的 Red Flags

```
❌ 跳过阶段 1 直接做阶段 2
❌ 阶段 1 发现问题，但"先看看阶段 2"
❌ 发现 Critical 问题，但标注为 Minor
❌ "差不多就好了" — spec 合规必须逐条核对
❌ review 完成但没有明确的通过/未通过结论
```

## review 后需要补写文档时：信息写入路由

review 发现需要补充规则或文档时，先判断类型再落笔：

| 内容类型 | 写入位置 |
|---------|---------|
| 产品交互行为规则 | `docs/product/` 对应文件 |
| 开发踩坑 / 经验 | `LEARNINGS.md` 或 `tasks/knowledge/lessons.md` |
| 需求 / AC 变更 | `tasks/prd/` 对应 PRD 文件 |
| 架构 / 产品决策 | `project-management/decision-log.md` |
| AI 协作规则 | `AGENTS.md` 或 `skills/` 对应 SKILL.md |

**禁止把产品规则、踩坑记录、需求变更直接追加进 AGENTS.md 正文。**
