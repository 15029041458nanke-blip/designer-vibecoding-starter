# Skill: systematic-debugging

> **触发条件**：任何 bug / 测试失败 / 意外行为 / 功能不符合预期时，必须先执行本流程，禁止直接提 fix。

---

## 铁律

```
❌ 未完成 Phase 1（根因调查），禁止提出任何 fix
❌ 已尝试 3 次 fix 仍失败，禁止继续加 fix
✅ 3 次 fix 失败 → 停下来质疑架构，向用户上报
```

---

## Phase 1：根因调查（必须先完成，才能进入后续阶段）

### 1.1 读错误信息
- 完整读 stack trace，不跳过任何行
- 记录：文件名、行号、错误类型
- TS/lint 报错通常直接包含答案

### 1.2 能否稳定复现
- 找到最小复现路径（步骤越少越好）
- 如果不能稳定复现 → 先收集更多数据，不猜测

### 1.3 最近改了什么
- `git --no-pager diff HEAD~1` 或 `git --no-pager log --oneline -5`
- 检查最近的改动，特别是本轮 session 的改动
- **优先怀疑最近改动**，而不是遗留代码

### 1.4 多层系统：加诊断日志
```
对每个组件边界：
- 记录进入时的输入值
- 记录离开时的输出值
- 确认环境/配置是否正确传递
运行一次，收集证据，再分析
```

### 1.5 追溯数据流
- 从报错位置往上追：谁调用了这里？传入了什么值？
- 持续往上追，直到找到"坏值最初来自哪里"
- 在源头修复，不在症状处修复

---

## Phase 2：模式分析（找根因之前，先理解正确模式）

1. 找**可工作的类似代码**：同一 codebase 里，相似功能是怎么做的？
2. **对比差异**：工作的 vs 不工作的，列出所有差异，哪怕看起来不重要
3. 理解依赖：这个功能依赖什么环境、配置、状态？

---

## Phase 3：假设与验证

1. **写出假设**：明确说"我认为根因是 X，因为 Y"
2. **最小化验证**：一次只改一个变量，不要同时改多处
3. 验证失败 → 形成新假设，重新来，**不要在旧假设上叠加 fix**

---

## Phase 4：实施修复

1. 先写失败的测试（确认能复现问题）
2. 实施最小 fix（只改根因，不顺手改其他）
3. 验证测试通过，且无回归

### 如果 Fix 不成功
```
第 1 次 fix 失败 → 回 Phase 1，重新收集证据
第 2 次 fix 失败 → 回 Phase 2，更仔细对比差异
第 3 次 fix 失败 → 停！质疑架构，向用户上报
```

**第 3 次失败的信号**：每次 fix 都在不同地方暴露新问题 → 很可能是架构设计问题，不是单点 bug。

---

## Red Flags（发现这些想法时，立刻停下来）

```
"快速试一下改这里看看"            → 回 Phase 1
"应该是这里的问题，我改改"        → 先写出假设再改
"加多一个判断就好了"              → 先找根因
"再试一次，这次换个思路"（第3次）  → 停，上报用户
"先 workaround，之后再看"         → 不允许，必须根因修复
```

---

## 常见误区

| 误区 | 现实 |
|---|---|
| "这个问题看起来简单，不需要流程" | 简单问题也有根因，流程反而更快 |
| "我已经知道问题在哪" | 知道症状 ≠ 知道根因，仍需验证 |
| "先改了看效果再说" | 多改多乱，一次只改一个变量 |
| "第3次了还没好，再改一次" | 第3次失败 = 架构问题，需要上报 |
